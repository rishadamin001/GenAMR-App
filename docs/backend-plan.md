# Backend design and verification boundary

## 1. Minimal schema and relationships
Eight requested tables are defined by the migration. Hospitals have many samples; samples have many qPCR runs, Sanger runs, predictions and AST confirmations. The knowledge base is shared reference data. Model versions are owner-scoped. UUID primary keys, foreign keys, child indexes, species/target JSON and arrays, S/I/R checks, Ct and probability bounds, unique sample codes per owner, and consistency between reflex status and the sequencing fee are enforced in SQL. Foreign key deletions are restrictive. Hospital codes and knowledge marker names are unique. Nullable metrics represent absent denominators rather than fabricated zero error.

## 2. Access rules and identity
Anonymous users: reference-table reads only. Authenticated users: reference reads plus read/insert/update for owned samples and model records; assay and confirmation ownership follows the sample. Confirmation logger must match the verified identity. Delete grants are withheld. RLS is enabled on all eight tables. Persona/hospital selectors are presentation controls, never authorization. Ownership uses auth.uid(), not user-editable metadata. Publishable keys are allowed in the browser; service-role keys are forbidden. No server privileges, views, storage buckets, scheduled jobs or security-definer functions are used.

## 3. Migration and recovery
Target is a fresh, dedicated free-tier research project, if provided. Inspect existing schema and migration history before applying. Apply the additive migration in a transaction, then verify grants, policies, indexes, constraints, and the seeded reference data. Do not reset an existing database. Application rollback preserves local storage and remote data. Schema corrections should be forward migrations; destructive rollback is not promised. Cloud upserts use stable owner-specific IDs and serialized uploads. A restorable snapshot is published after normalized uploads finish. A failed batch retains all local data and can be retried. The normalized tables are not a transactionally published clinical data product. After a QC failure or changed reflex decision, previously uploaded prediction/Sanger rows can remain as historical artifacts; the snapshot and current qPCR QC flag govern display. Do not consume those tables independently as current clinical reports.

## 4. Fixtures and checks
66 deterministic synthetic samples, six interactive archetypes, eight hospital reference profiles, and eight regional referral catchments. No real patient data. TypeScript and browser tests cover local mode, state changes, QC hold, corrupted snapshot rejection, offline persistence and derived fees. Required live checks: owner A/B isolation, anonymous denial on private tables, owner-change rejection, forged logger rejection, restricted deletion, constraint violations, retry after a partial upload, and snapshot round-trip. **Live SQL/RLS verification has not run: the connected Supabase account returned no projects.** No project was provisioned and no database was mutated.
